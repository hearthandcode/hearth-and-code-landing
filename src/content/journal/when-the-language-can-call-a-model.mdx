I shared a [public account of HCAN](/journal/hcan-condensed-symbolic-language/) as a condensed language for human–agent communication. Its grammar helps a person name an intent, a source, a return shape, and a guard without hiding the boundary in a paragraph. Alongside it I have been building Sigil, a different language: a constrained S-expression system for writing the computation an agentic workflow actually performs. HCAN is not Sigil syntax, and Sigil does not replace human conversation.

The new development is concrete. A Sigil program has now made an admitted call to a local language model, received a typed answer, checked it, and recorded a receipt. I want to explain the seam, because the interesting question is not whether code can call a model. Of course it can. The question is what the code must say before that call is allowed, and what the reader can know afterward.

## Three ways to point, without pretending they are the same

HCAN's recent work sharpened how a message refers to its world. An `@` reference points to an accountable source or location. A `$` reference names a concept: an idea that can be compared or discussed without pretending it is a file. A `~` reference marks an approximation. One line can carry all three. A name for an idea is useful; it is not evidence for a claim about the world. If a line has only conceptual or approximate referents, HCAN still asks for a context binding.

The same insistence on distinctions has reached effects. Network and execute joined read, compute, and write as named effect classes. When tags combine, a closed rule table can record interactions: write × network becomes data-egress; read × network becomes data-ingress; execute × network becomes remote-execute. More recent structured bindings and scoped guards refine what those effects touch. These are descriptions and checks, not a self-issued permission slip. A tool's ability to send data is different from the authority to send *this* data on *this* task.

The medium has also grown an opt-in vocabulary loader and a collection of multiline example programs. The core grammar stays small while particular domains can say more. I do not want to blur this work into a claim that HCAN is a runtime; it remains a communication medium with validators and editor surfaces.

## A program reaches the model

Sigil makes the next step executable under a separate set of conditions. A program defines a request record, a response sum, and a delegation schema. A function that delegates must declare the particular `llm/Request` effect. The checker rejects a missing declaration. At evaluation time, the schema needs an admitted capability and a matching route. A name in a provider registry alone grants nothing.

In schematic Sigil, the crossing looks like this:

```text
(defrecord BonsaiRequest ((goal Text)))
(defdata BonsaiResponse (Ok Text) (Refused Text))
(delegation-schema BonsaiRequest BonsaiResponse)

; inside a function declaring (:effects (llm/BonsaiRequest)):
(match (delegate (record BonsaiRequest ((goal "Reply briefly"))))
  ((Ok answer) answer)
  ((Refused reason) reason))
```

The abbreviated function body above illustrates the type and refusal shape; it is not a copy-paste standalone program or the exact live prompt. In the owner-authorized canary, a local Bonsai 27B served through `obsidian-sglang` returned `(Ok "bonsai is live")`. Sigil checked the response against the declared sum and recorded `outcome=provider-executed` and `deviation=none`. That is evidence of *one successful call*, not proof that all prompts, routes, or providers behave well.

Refusal has its own ordinary branch. Backend failure is a different lane, with a typed error and an explicitly declared fallback where available. A policy stop is not a model refusal and cannot be wished away by matching on `Refused`. When a response fails its shape, deviation details identify the constructor or field at issue. The receipt's digest is currently non-cryptographic; I would not use it as an integrity guarantee.

## Why the toolchain stays outside the call

The reader, checker, formatter, and language server do not contact a model. That is a design boundary, not a lack of ambition. It means an editor can inspect a program offline without silently turning editing into execution. The evaluator can then delegate only under a named runtime admission. The same program can be checked without an available provider and evaluated only in an environment that has chosen its route and limits.

This is also where my confidence stops. There are offline tests of the reader, types, evaluation, routes, and mock transport, and the one live canary. There is not yet independent qualification of every provider, end-to-end aggregate budgets, or attenuation of authority per call site. The other registered providers remain pending adapters; they do not become live because they appear in a table. A structural response check is not a judgment that the answer is correct or useful.

HCAN can help a human say what kind of action is intended and what guard must hold. Sigil can check a bounded computation and produce evidence about an admitted effect. Neither language makes the human decision for us. The next useful experiment is to ask whether these explicit boundaries make a real task easier to review and correct than a simpler program or prompt. If they do not, the simpler route should win.
